## Часть A — Надёжность

### A.1 Общий http-хелпер `_lk_fetch` для функций сообщений ЛК

**Завершение A.1 фазы 4.** В фазе 4 ретраи (`_lk_fetch`) получили только
`login`, `get_raw_timetable`, `click_start_lesson`. Функции работы с
сообщениями ЛК остались на «голых» запросах.

**Проблема:** `DebuggableBonchAPI.get_messages_page`, `get_message` и
модульные `lk_search_recipients`, `lk_upload_file`, `lk_send_message` делают
`session.get/post` + `await response.text()` без ретраев. Первая же ошибка
сети/таймаут ловится `except` и оборачивается в «пустой» результат:
- `get_messages_page` → `{'messages': [], 'total_pages': 1}` — пользователь
  видит ложное «нет сообщений»;
- `lk_send_message` → `False` — ложное «не удалось отправить»;
- `lk_search_recipients` → `[]` — ложное «получатель не найден».

**Что сделать:** провести эти запросы через `_lk_fetch` (ретраи с
экспоненциальным бэкоффом, устойчивое чтение тела). Сессии/cookie/семафор —
без изменений, как в фазе 4.

**Особый случай — `lk_upload_file`:** загрузка идёт `multipart/form-data`
через `aiohttp.FormData`, а `FormData` одноразовый — повторное использование
после неудачной отправки невалидно. При выполнении решить: пересобирать
`FormData` на каждую попытку (читать файл заново) или не ретраить именно
загрузку (ретраить только финальную отправку сообщения). По умолчанию —
не ретраить тело загрузки, чтобы не плодить дубль-файлы в ЛК.

**Риск:** средний. Делать под защитой `test_lk_client.py` — расширить его
сценариями сообщений (ретрай при сбое, частичный сбой), как в фазе 4.

**Проверка:** имитация разового сетевого сбоя при опросе сообщений →
запрос повторяется, ложного «нет сообщений» нет; `pytest` зелёный.

## Часть B — Структура

### B.1 Разрезать `generate_timetable_image_from_dict`

**Проблема:** `rendering.py:generate_timetable_image_from_dict` — **одна
функция на ~470 строк** (самая длинная в проекте). Внутри — расчёт раскладки,
отрисовка заголовка, колонок, блоков дней, ячеек занятий, футера. Читать и
менять тяжело.

**Что сделать:** извлечь связные под-функции (расчёт высот/раскладки,
отрисовка блока дня, отрисовка ячейки занятия, заголовок/футер). Чистая
декомпозиция — поведение пиксель-в-пиксель не меняется.

**Риск:** низкий–средний. У `rendering.py` только smoke-тесты (PNG создаётся,
не пуст) — дрейф вёрстки они не поймают. Снижаем риск механическим
извлечением (вырезал блок → функция с теми же локальными переменными как
параметрами, тело дословно).

**Проверка:** `test_rendering.py` зелёный; визуально картинка расписания
группы не изменилась.

### B.2 Разгрузить `lk_client.py`

**Проблема:** `lk_client.py` — **823 строки**, самый большой файл проекта.
Смешивает: `_lk_fetch`, класс `DebuggableBonchAPI` (вход, расписание,
автоклик, сообщения), аксессоры реестров (`get_timetable_api`,
`get_message_api`), хелперы дебаг-дампов (`_prune_debug_dumps`,
`save_debug_dump`) и модульные функции сообщений (`lk_search_recipients`,
`lk_upload_file`, `lk_send_message`).

**Что сделать:** вынести домен сообщений в `lk_messages.py` — модульные
функции `lk_search_recipients/upload/send` переносятся чисто. Методы
`get_messages_page`/`get_message` — это методы `DebuggableBonchAPI`:
переносить их можно только через миксин (`LkMessagesMixin` в `lk_messages.py`,
`class DebuggableBonchAPI(BonchAPI, LkMessagesMixin)`).

**Решить при выполнении:** полный вынос домена сообщений (миксин + функции,
−~350 строк) или лёгкий (только 3 модульные функции + дебаг-дампы, −~200
строк, класс не трогаем). По умолчанию — взвесить churn миксина против
косметической пользы; класс трогать в последнюю очередь.

**Риск:** низкий — механический перенос + правка импортов (приём как C.1
фазы 4). Делать **после A.1** — A.1 правит функции сообщений на месте,
B.2 переносит уже доработанные.

**Проверка:** `pytest` зелёный; импорты `lk_client` снаружи не сломаны.

## Часть D — Footprint

### D.1 Снизить RAM-footprint расписания

**Проблема:** `timetable.json` ~71 МБ (404 группы, 90 213 занятий). При
старте `load_from_json` парсит его в `all_groups_timetable_cache` и держит в
памяти. Замер: `json.load` → **~105 МБ резидентно, пик ~274 МБ**. Каждое
занятие — словарь из 13 строковых полей; значения (дни недели, времена,
предметы, ФИО преподавателей, корпуса, группы) повторяются тысячекратно, но
Python их не интернит — в RAM лежат сотни тысяч копий одинаковых строк.

**Что сделать:** интернировать повторяющиеся строки при загрузке —
`json.load(..., object_hook=...)` интернит ключи и строковые значения каждого
объекта прямо в ходе парсинга (заодно снижает и пик). Замер с интернингом:
**~41 МБ** вместо 105 (−60%).

**Точку интернинга решить при выполнении:** на пути загрузки из JSON
(`public_timetable.load_from_json` — частый случай, старт бота) интернинг
через `object_hook`; на пути сетевого рефреша (`all_groups_timetable_with_progress`)
кэш строится заново и не интернирован — добавить единый проход интернинга при
присваивании `all_groups_timetable_cache`, либо интернить в
`parsers.parse_timetable_table`.

**Риск:** низкий — интернинг строк семантику не меняет (строки иммутабельны).

**Проверка:** замер RAM до/после на реальном `timetable.json`; кэш расписания
читается корректно; `pytest` зелёный.

## Что сознательно не делаем

| Идея | Почему |
|------|--------|
| Полный реверс `bonchapi` | высокий риск; используется лишь базовый класс и `parser.get_lesson_id` как фолбэк |
| CI (GitHub Actions) | деплой через Coolify, см. v2 §2.1 |
| PostgreSQL вместо SQLite | мало пользователей |
| Веб-панель | Telegram достаточно |
| Ленивая загрузка расписания по группам / SQLite-хранилище расписания | D.1 (интернинг строк) даёт −60% RAM дёшево и без риска; ленивая загрузка/БД — отдельное крупное решение (L+), браться, только когда footprint станет реальной проблемой |

## Рекомендованный порядок работ

```
Быстрая победа, низкий риск:
  D.1 (footprint расписания)

Надёжность:
  A.1 (_lk_fetch для функций сообщений)

Структура:
  B.2 (разгрузить lk_client.py — после A.1) → B.1 (разрезать рендер картинки)

Тесты:
  C.1 (устойчивость и покрытие LessonController)
```

**Логика порядка:**
- D.1 — изолированная быстрая победа, ни от чего не зависит.
- A.1 — приоритетная надёжность; правит функции сообщений на месте.
- B.2 — после A.1: переносит уже доработанные функции сообщений, не нужно
  чинить дважды.
- B.1 — независимая декомпозиция рендера.
- C.1 — ядро автоотметки; делается отдельно, ни от чего не зависит, но
  объёмнее прочих — берётся последним.
