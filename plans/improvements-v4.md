## Часть A — Надёжность

### A.1 Общий http-хелпер с ретраями для LK-клиента

**Перенос из v3 (под-пункт A.1, сознательно отложен).**

**Проблема:** `TImetabels.get_timetable` повторяет запрос до 3 раз при сбое
сервера, а `DebuggableBonchAPI` (`login`, `get_raw_timetable`,
`click_start_lesson`) делает запросы без ретраев — первая же ошибка сети/ЛК
роняет операцию (вход, автоотметку, напоминание).

**Что сделать:**
- Общий async http-хелпер: единые `BROWSER_HEADERS`/таймаут, устойчивое чтение
  тела (`read()` + decode `errors='replace'` — как в фиксе `_get_timetable_once`),
  ретраи с экспоненциальным бэкоффом.
- Провести запросы `DebuggableBonchAPI` через хелпер.
- Не ломать существующее: cookie_jar, `proxy=None`, `get_lk_semaphore()`.

**Риск:** средний — трогает авторизацию и автоотметку. Делать последним, под
защитой `test_lk_client.py` (расширить при необходимости).

**Проверка:** автоотметка и вход работают; `pytest` зелёный.

### A.2 Защитное чтение в `TImetabels.get_groups`

**Проблема:** в v3 `_get_timetable_once` сделали устойчивым к телу, не
декодируемому в UTF-8. Но `get_groups` (список факультетов/групп) по-прежнему
вызывает `await response.text()` **без** `try/except` — битый ответ уронит
весь рефреш расписания (`get_groups` запускается первым в загрузке).

**Что сделать:** применить тот же приём — `read()` + decode `errors='replace'`,
обернуть в `try/except` с понятным логом и фолбэком (пустой список групп /
переброс с понятной ошибкой).

**Проверка:** при битом ответе на список групп рефреш не падает с трейсбеком.

### A.3 Гарантированно-периодический рефреш расписания

**Перенос из v3 (часть C, отмечено как будущая доработка).**

**Проблема:** рефреш `timetable.json` сейчас ленивый — срабатывает по TTL
только при вызове `get_all_groups_timetable` (открытие расписания группы/
преподавателя/аудитории). Если расписание группы никто не открывает,
рефреша нет — и уведомления об изменении расписания (C.1) не срабатывают.
C.1 держится именно на «бот и так периодически перезагружает timetable.json»
— а сейчас это не гарантировано.

**Что сделать:** фоновая задача (по образцу `message_poll_loop` из C.2) —
раз в N часов (env, напр. `TIMETABLE_REFRESH_MIN`) вызывает
`_refresh_timetable_quietly`. Так дифф C.1 считается регулярно.

**Проверка:** при старте бота поднимается фоновый цикл; через интервал
расписание перечитывается, дифф C.1 отрабатывает без действий пользователя.

### A.4 Почистить остаточный ruff

**Что нашлось:** после v3 `ruff check .` оставляет 9 ошибок, не попавших в
scope A.2 v3 (там чистили только импорты):
- 3× `F841` — неиспользуемые переменные в `rendering.py`
  (`lesson_type_colors`, `default_color`, `emoji_font_tiny`);
- 6× `F541` — f-строки без подстановок в `handlers/messages.py`.

**Что сделать:** убрать мёртвые переменные, снять лишний `f`-префикс.
Цель — `ruff check .` без ошибок.

## Часть B — Фичи / UX

### B.1 Тумблеры уведомлений в профиле

**Перенос из v3 (часть C, отмечено как будущая доработка).**

**Проблема:** уведомления C.1 (изменения расписания) и C.2 (новые сообщения
ЛК) приходят **всем** авторизованным пользователям без возможности отключить.
Кого-то это раздражает — нужны переключатели.

**Что сделать:**
- Колонки `notify_schedule_enabled` / `notify_messages_enabled` в `users`
  (миграция как в `db.py`, по умолчанию вкл), хелперы get/set.
- Пункты в меню профиля (рядом с настройкой напоминаний о парах).
- Проверка флага: `notify_schedule_changes` шлёт только подписанным
  пользователям группы; `check_new_messages_for_user` уважает флаг.

**Проверка:** выключенный тумблер — уведомления не приходят; включённый —
приходят; настройка переживает перезапуск.

### B.2 Полное ФИО в картинке личного расписания

**Проблема:** в v3 (доработка B.1+) обогатили полным ФИО **текст** личного
расписания. Картинка личного расписания (`rendering.generate_timetable_image`,
формат объектов) по-прежнему показывает краткое ФИО.

**Что сделать:** прокинуть в `generate_timetable_image` расписание группы
(как в `format_timetable`) и подставлять полное ФИО по (день недели, время,
предмет). Корпус в картинке — разбить из `location` (там он уже есть).

**Проверка:** на картинке личного расписания — полное ФИО (с фолбэком на
краткое) и корпус.

### B.3 Периодическое переопределение группы

**Проблема:** `detect_user_group` (C.0) срабатывает при логине и на старте
бота, если группа неизвестна. Между семестрами группа меняется — повторного
определения нет.

**Что сделать:** переопределять группу периодически — например, в фоновой
задаче A.3 заодно обновлять `group_name` авторизованных пользователей.
Объём S, если делать поверх A.3.

## Часть C — Тесты и структура

### C.1 Разрезать `handlers/messages.py`

**Проблема:** `handlers/messages.py` — **806 строк**, снова локальный монолит
(второй по размеру файл после разреза `schedule.py` в A.2b v3). После B.2
(flow вложения файла) вырос ещё.

**Что сделать:** разрезать по поддоменам — чтение входящих (список, навигация,
открытие сообщения) vs отправка (выбор получателя, тема, текст, вложение).
Под-пакет `handlers/messages/` с `__init__.py`, агрегирующим роутеры, либо
плоские файлы — решить при выполнении. Приём — как A.2b v3: Router per file,
поведение дословно, precedence не меняется.

**Риск:** низкий — повторение приёма A.2b. Тесты: зелёные.

### C.2 Покрытие хэндлеров messages/autoclick/common/profile

**Проблема:** A.4 v3 поднял покрытие расписания (64–80%) и сервисов (76–91%),
но остальные хэндлеры — низко: `handlers/messages.py` 23%, `autoclick.py` 18%,
`common.py` 27%, `profile.py` 35%.

**Что сделать:** точечные тесты ключевых хэндлеров через фейковые
`Message`/`CallbackQuery` (паттерн `test_handlers_schedule.py`,
`test_handlers_messages.py`). Делать после C.1 — тесты сразу под новую
структуру. Цель — критичные хэндлеры выше 60%.

## Рекомендованный порядок работ

```
Быстрые, низкий риск:
  A.4 (ruff) → A.2 (защита get_groups)

Надёжность и управляемость уведомлений:
  A.3 (периодический рефреш) → B.1 (тумблеры уведомлений)

Структура и тесты:
  C.1 (разрезать messages.py) → C.2 (покрытие хэндлеров)

Доводка:
  B.2 (ФИО в картинке) → B.3 (переопределение группы, поверх A.3)
  → A.1 (http-хелпер — самый рискованный, последним)
```

**Логика порядка:** A.4/A.2 — быстрые победы. A.3 чинит фундамент под C.1
из v3 (без периодического рефреша уведомления об изменении расписания почти
не срабатывают), поэтому раньше. B.1 — важный UX (неуправляемые уведомления
раздражают). C.1 перед C.2 — чтобы тесты писать сразу под новую структуру.
A.1 — самый рискованный (авторизация/автоотметка), делать последним.
