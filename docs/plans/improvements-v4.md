## Часть A — Надёжность и уборка репозитория

### A.1 Общий http-хелпер с ретраями для LK-клиента

**Перенос из v3 (под-пункт A.1, отложен).** **Обязательный пункт закрытия
фазы 4** — не «по желанию». Делается последним только из-за риска (трогает
авторизацию/автоотметку), а не из-за низкой важности. Если фаза рвётся по
времени — A.1 переходит ПЕРВЫМ пунктом v5, а не отбрасывается.

**Проблема:** `TImetabels.get_timetable` повторяет запрос до 3 раз при сбое
сервера, а `DebuggableBonchAPI` (`login`, `get_raw_timetable`,
`click_start_lesson`) делает запросы без ретраев — первая же ошибка сети/ЛК
роняет операцию (вход, автоотметку, напоминание).

**Что сделать:**
- Общий async http-хелпер: единые `BROWSER_HEADERS`/таймаут, устойчивое чтение
  тела (`read()` + decode `errors='replace'` — как в фиксе `_get_timetable_once`),
  ретраи с экспоненциальным бэкоффом.
- Провести запросы `DebuggableBonchAPI` через хелпер.
- Не ломать существующее: cookie_jar, `proxy=None`, `get_lk_semaphore()`.

**Риск:** средний. Делать под защитой `test_lk_client.py` — при необходимости
сначала расширить его (сценарии ретраев, частичных сбоев).

**Проверка:** автоотметка и вход работают; имитация сбоя сети → запрос
повторяется; `pytest` зелёный.

### A.2 Защитное чтение в `TImetabels.get_groups`

**Проблема:** в v3 `_get_timetable_once` сделали устойчивым к телу, не
декодируемому в UTF-8. Но `get_groups` (список факультетов/групп) по-прежнему
вызывает `await response.text()` **без** `try/except` — битый ответ уронит
весь рефреш расписания (`get_groups` запускается первым в загрузке).

**Что сделать:** применить тот же приём — `read()` + decode `errors='replace'`,
обернуть в `try/except` с понятным логом и фолбэком.

**Проверка:** при битом ответе на список групп рефреш не падает с трейсбеком.

### A.3 Фоновая задача: периодический рефреш + переопределение групп

**Перенос из v3 (часть C, отмечено как будущая доработка). Сюда же свёрнут
бывший B.3** (переопределение группы) — по замечанию ревью обе вещи делает
одна фоновая задача.

**Проблема:**
- Рефреш `timetable.json` сейчас ленивый — по TTL только при вызове
  `get_all_groups_timetable`. Если расписание группы никто не открывает,
  рефреша нет → уведомления C.1 (изменения расписания) не срабатывают.
- `detect_user_group` (C.0) определяет группу при логине / на старте, если
  она неизвестна. Между семестрами группа меняется — переопределения нет.

**Что сделать:** одна фоновая задача (по образцу `message_poll_loop` из C.2),
раз в N часов — env `TIMETABLE_REFRESH_HOURS` (дефолт `6`, как
`TIMETABLE_TTL_HOURS`; не путать с минутами):
1. вызывает `_refresh_timetable_quietly` → дифф C.1 считается регулярно;
2. переопределяет `group_name` авторизованных пользователей.

**Частоты развести.** Рефреш расписания — каждый тик (`TIMETABLE_REFRESH_HOURS`).
Переопределение групп — НЕ каждый тик: `detect_user_group` — это сетевой запрос
в ЛК на каждого пользователя, а группа меняется ~раз в семестр. Делать его
раз в сутки (или раз в N тиков) — иначе лишняя нагрузка на ЛК и риск антибота.

Добавить переменную в `.env.example` с комментарием.

**Проверка:** при старте поднимается фоновый цикл; через интервал расписание
перечитывается (дифф C.1 отрабатывает без действий пользователя); группа
пользователя переопределяется по своему, более редкому графику.

### A.5 Уборка репозитория («витрина GitHub»)

**Проблема (по замечанию ревью):** v3 навёл порядок в *коде* (модули,

- ~25 `.py`-файлов вперемешку с шрифтами в корне;
- 5 шрифтов (`G8.otf`, `Montserrat-SemiBold.ttf`, `NotoColorEmoji.ttf`,

  (`test_main_config`/`formatting`/`keyboards`/`lesson_logic`/`security`/

**Что сделать:**
- Шрифты → `assets/fonts/`; поправить пути в `rendering.py` и `Dockerfile`.
- `TImetabels.py` → осмысленное имя (напр. `public_timetable.py`); обновить

  `BonchAPI` — опционально.
- `test_main_*.py` → `test_config.py`, `test_formatting.py` и т.д.
  (нулевой риск — pytest находит `test_*.py`).
- **Решить при выполнении:** ограничиться лёгкой уборкой (выше) или вводить
  пакетную раскладку `src/` — взвесить churn (каждый импорт + `Dockerfile`

  лёгкая уборка; полный `src/`-пакет — отдельным решением.

**Проверка:** `pytest` зелёный; `docker compose up` собирается; корень
репозитория читаемый.

## Часть B — Фичи / UX

### B.1 Тумблеры уведомлений в профиле

**Перенос из v3 (часть C, отмечено как будущая доработка).**

**Проблема:** уведомления C.1 (изменения расписания) и C.2 (новые сообщения
ЛК) приходят **всем** авторизованным пользователям без возможности отключить.

**Что сделать:**
- Колонки `notify_schedule_enabled` / `notify_messages_enabled` в `users`
  (миграция как в `db.py`, по умолчанию вкл), хелперы get/set.
- Пункты в меню профиля (рядом с настройкой напоминаний о парах).
- Проверка флага: `notify_schedule_changes` шлёт только подписанным
  пользователям группы; `check_new_messages_for_user` уважает флаг.

**Проверка:** выключенный тумблер — уведомления не приходят; включённый —
приходят; настройка переживает перезапуск.

### B.2 Полное ФИО в картинке личного расписания

**Проблема:** в v3 (доработка B.1+) обогатили полным ФИО **текст** личного
расписания. Картинка (`rendering.generate_timetable_image`, формат объектов)
по-прежнему показывает краткое ФИО.

**Что сделать:** прокинуть в `generate_timetable_image` расписание группы
(как в `format_timetable`) и подставлять полное ФИО по (день недели, время,
предмет). Корпус — разбить из `location`.

**Проверка:** на картинке личного расписания — полное ФИО (с фолбэком на
краткое) и корпус.

## Часть C — Тесты и структура

### C.1 Разрезать `handlers/messages.py`

**Проблема:** `handlers/messages.py` — **806 строк**, снова локальный монолит
(второй по размеру файл после разреза `schedule.py` в A.2b v3). После B.2

**Что сделать:** разрезать по поддоменам — чтение входящих (список, навигация,
открытие сообщения) vs отправка (выбор получателя, тема, текст, вложение).
Под-пакет `handlers/messages/` с `__init__.py`, агрегирующим роутеры, либо
плоские файлы — решить при выполнении. Приём — как A.2b v3: Router per file,
поведение дословно, precedence не меняется.

**Риск:** низкий — повторение приёма A.2b. Тесты: зелёные.

### C.2 Покрытие хэндлеров — 8 явных сценариев

**Проблема:** A.4 v3 поднял покрытие расписания (64–80%) и сервисов (76–91%),
но остальные хэндлеры — низко: `handlers/messages.py` 23%, `autoclick.py` 18%,
`common.py` 27%, `profile.py` 35%.

**Что сделать (конкретные кейсы, а не «>60%» в воздухе).** Точечные тесты
через фейковые `Message`/`CallbackQuery` (паттерн `test_handlers_schedule.py`,
`test_handlers_messages.py`). Делать **после C.1 и B.1** — тесты под новую
структуру `handlers/messages/` и новые тумблеры профиля.

**Must-have (1–5)** — без них фазу 4 не закрываем:

1. **messages — тёплый кэш:** `cmd_messages` при свежем кэше показывает список
   без перезапроса ЛК; при устаревшем — перезапрашивает первую страницу.
2. **messages — навигация:** `handle_message_callback` (prev/next), включая
   ленивую подгрузку следующей страницы при достижении конца загруженной.
3. **messages — `cmd_send_lk`:** парсинг аргументов — числовой ID vs
   «Фамилия И.О. + текст» (граница ФИО/текста).
4. **autoclick — тумблер:** включение/выключение автоотметки из меню,
   состояние сохраняется в БД (`autoclick_enabled`).
5. **common — `/login`:** успех/неуспех через `perform_login`, учёт
   rate-limit.

**Should-have (6–8)** — желательны, но при нехватке времени можно отложить в v5:

6. **common — `/start` и `/cancel`:** онбординг/регистрация; `/cancel`
   сбрасывает FSM-состояние; fallback-хэндлер на нераспознанный ввод.
7. **profile — напоминания о парах:** меню уведомлений (вкл/выкл, выбор
   минут), выход из ЛК.
8. **profile — тумблеры B.1:** вкл/выкл уведомлений об изменении расписания
   (C.1) и о новых сообщениях ЛК (C.2); флаги `notify_schedule_enabled` /
   `notify_messages_enabled` в БД; при выкл — соответствующие пуши не шлются.

**Проверка:** сценарии 1–5 покрыты; при полном закрытии — все 8. Критичные
хэндлеры выше 60%.

| Полный реверс `bonchapi` | высокий риск; доработка B.1+ закрыла главную боль (полное ФИО в личном расписании — через кросс-ссылку на расписание группы) |

внутри A.5 (по умолчанию — лёгкая уборка).

## Рекомендованный порядок работ

```
Быстрые, низкий риск:
  A.4 (ruff) → A.2 (защита get_groups) → A.5 (уборка репозитория)

Надёжность и управляемость уведомлений:
  A.3 (фоновый рефреш + переопределение групп) → B.1 (тумблеры уведомлений)

Структура и тесты:
  C.1 (разрезать messages.py) → C.2 (8 сценариев; после B.1)

Доводка:
  B.2 (ФИО в картинке) → A.1 (http-хелпер — обязательный, последним из-за риска)
```

**Логика порядка:**
- A.4/A.2/A.5 — быстрые победы; A.5 раньше, т.к. переименование `TImetabels.py`
  трогает импорты — пусть последующие задачи работают с новым именем.
- A.3 чинит фундамент под C.1 из v3 (без периодического рефреша уведомления об
  изменении расписания почти не срабатывают), поэтому раньше фич.
- B.1 — важный UX: неуправляемые уведомления раздражают.
- C.1 перед C.2 — тесты писать под новую структуру `handlers/messages/`.
- C.2 после B.1 — сценарий 8 проверяет тумблеры, которых ещё нет до B.1.
- **A.1 — последним из-за риска** (авторизация/автоотметка), но это
  обязательный критерий закрытия, не опциональный «довесок». Если по A.1 уже
  было откладывание в v3 — здесь он зафиксирован в критериях ниже.
